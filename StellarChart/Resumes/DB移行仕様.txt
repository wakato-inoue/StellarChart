StellarChart DB移行仕様
========================
作成日: 2026-06-05

■ 現状の問題
-----------
- tasks / projects / transfers などのグローバル配列をコード全体で直接参照
- filter / find / push / 直接代入 が全ファイルに散在
- 「どこでデータを読んでいるか／書いているか」が一箇所に集約されていない

■ 移行方針
-----------
データアクセス層（Data Access Layer）を1つ作り、
全コンポーネントはそれ経由でのみデータを読み書きする。

理想の構成:
  js/
    data/
      schema.js        — 型定義・定数
      repository.js    — CRUD操作を全てここに集約
      api-client.js    — API呼び出し窓口
      mock-provider.js — 現状のモックデータ提供

■ 移行手順（案）
-----------------
Step 1: repository.js を作成し、以下のCRUD関数を定義
  - taskRepo.findAll() / findById() / findByProject() / save() / delete()
  - projectRepo.findAll() / findById() / save() / delete()
  - transferRepo.findAll() / save()
  - employeeMaster はマスタデータとして const 維持 or API化

Step 2: 各コンポーネントの グローバル配列直接参照 を repository 経由に置き換え
  - 例: tasks.filter(t => t.projectId === id)
    → taskRepo.findByProject(id)
  - 例: tasks.push(newTask)
    → taskRepo.save(newTask)

Step 3: モック → API への差し替え
  - mock-provider.js と api-client.js を repository.js 内で切り替え
  - 切り替えは repository.js 1ファイルの修正で完了

  // 子タスクも含めて再帰削除

taskRepo.saveProperty(task)         → void

【オブジェクトプロパティ変更の保存戦略】

現状ではタスクオブジェクトのプロパティを直接変更している箇所が多数ある。
DB移行時は以下の2パターンが考えられる:

パターンA: プロパティ変更後に毎回 taskRepo.saveProperty(task) を呼ぶ
  task.status = 'completed';
  taskRepo.saveProperty(task);  // 追加行
  // 確実だが漏れのリスクあり

パターンB: Proxy や setter で変更を検知して自動保存
  const task = taskRepo.findById(id);
  task.status = 'completed';  // Proxy が自動で save
  // 安全だが複雑。導入コストが高い

推奨: まずは パターンA で実装し、
      後日必要に応じて パターンB に移行するのが現実的。
